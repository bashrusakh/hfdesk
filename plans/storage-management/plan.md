## 1. Что должен получить пользователь

Пример: в папке лежат шесть вариантов модели. Пользователь выбирает Q4 и нажимает «Удалить».
Исчезает только выбранный файл Q4 или его известная группа частей.
Остальные пять вариантов, mmproj, tokenizer, config, README и другие места хранения остаются.
Сама папка модели и незавершённые загрузки также остаются.

Квант — вариант GGUF-модели; группа частей — файлы одного разбитого GGUF.
Если два разных семейства/группы файлов имеют метку `Q4_K_M`, пользователь выбирает конкретную группу.
Метка не означает «удалить всё, где встречается Q4»; поиск по подстроке не даёт такого права.
Обычный вариант, MTP-вариант и группы в разных подпапках показываются отдельно.

Для HF-кэша подтверждение охватывает выбранную группу во **всех сохранённых версиях**
одного выбранного HF-репозитория в одном выбранном месте хранения.
Это не разрешение удалить другую группу, другой репозиторий или другой корень.
Для локального хранения удаляются только выбранные записи файлов в выбранном месте.

Область работы — GGUF. Общий менеджер любых файлов, safetensors и datasets не добавляется.
Существующие операции с datasets должны сохранить своё поведение.
Существующий поиск и скачивание остаются; новое удаление не расширяет их назначения.

## 2. Где разрешено выбирать файлы

Выбор строится из известных приложению мест: `LocalDir`, настроенных маршрутов,
`LocalScanDirs` и фактических мест, которые приложение уже умеет сканировать.
Пользователь выбирает найденную строку, а не вводит произвольный путь в браузере.
Значок Local/Friendly объясняет отображение, но сам по себе не разрешает удаление.
Совпадение физического пути через другой псевдоним не расширяет разрешённую область.

**Удаление в `LocalScanDirs` явно разрешено пользователем.** Прежний запрет на DELETE там отменён.
Можно удалить найденный GGUF, даже если его скопировали вручную и HFDesk его не скачивал.
История загрузок, job или `hfd`-manifest для такого локального файла не требуются.
При этом папки сканирования не становятся автоматически местами для скачивания.

Перед удалением сервер заново проверяет выбранную группу, настройки корней и реальные пути.
Изменение настроек, вложенные корни и устаревший выбор нельзя обходить запасным путём.
Нельзя молча перейти к другому типу, месту хранения или более широкому удалению.
Если безопасность или точный состав неясны, операция отказывается с понятной причиной.

## 3. Локальное удаление и ссылки

Удаляются выбранные записи файлов, а не вся папка модели через `RemoveAll`.
Нельзя рекурсивно удалять всю friendly-папку или трогать соседние файлы и части загрузок.
Удаление пустых каталогов, если понадобится, только нерекурсивное; для результата оно не обязательно.

Ссылка вместо конечного файла не разрешает автоматически удалить её цель вне выбранной области.
Если удаляется только ссылка, UI прямо говорит: «Удалится ссылка, сам файл с весами останется».
Если этот результат нельзя безопасно определить, нужен видимый отказ, а не ручной ввод пути.
Для связанных friendly-ссылок связь с выбранным содержимым доказывается до удаления содержимого.
При такой дополнительной очистке HF-ссылок невыбранные обычные файлы в friendly-папке сохраняются.
Но явно выбранный обычный GGUF там — локальный файл, который можно удалить после подтверждения.
Даже под значком Friendly его нельзя направлять на удаление HF-данных или скрывать «Удалить».
Неясная цепочка ссылок означает видимое предупреждение или отказ, а не догадку.
Подтверждение объясняет, какие записи исчезнут и что известно об освобождении места.

## 4. Особенности HF-кэша

Blob — сам файл с данными; snapshot — папка сохранённой версии.
Friendly — удобные имена/ссылки для просмотра этих файлов.

В обычной схеме `HFCache`/`RepoDir` содержимое blob относится к репозиторию;
snapshot ссылается на blob, а friendly-представление — на snapshot.
`hfd`-manifest перезаписывается заданием и не является полным списком всех сохранённых файлов.
`refs/main` указывает версию; это не счётчик ссылок на отдельный файл.

Нужно прочитать реальные связи в пределах выбранного репозитория и места хранения.
Удаляются выбранные конечные записи в snapshot и связанные friendly-ссылки.
Blob можно удалить, только если оставшиеся связи в этом репозитории больше его не требуют.
Если он нужен другой группе, сохраняются blob и необходимые промежуточные записи;
если такую цепочку нельзя безопасно обработать, операция отказывается.
Неизвестные связи нельзя считать отсутствующими: содержимое сохраняется либо выдаётся отказ.
Глобальное доказательство всех ссылок во всей произвольной файловой системе не требуется.

Для обычных файлов внутри snapshot и неожиданного внешнего кэша без понятных связей
нужно корректное сопоставление с выбранным квантом либо объяснение, почему оно невозможно.
Однако обычные скачивания самого HFDesk нельзя молча объявить неподдерживаемыми.
Обычная HF-структура уже реализована: сначала сохраняется blob, затем создаются snapshot/friendly-ссылки.
На Linux предусмотрена эта стандартная структура; при пропуске уже скачанного blob загрузчик воссоздаёт ссылки.
Общее утверждение «HF-кэш сохраняется неправильно» не доказано и отозвано.
В проверенной версии main на Windows создание snapshot/friendly-ссылок пропускается с предупреждением;
байты до этого уже сохранены. Копии или жёсткие ссылки вместо этих имён не создаются.
Manifest перезаписывается каждым заданием, но имена старых файлов могут оставаться в сохранённых заданиях
(`jobs_state`, `Files[].Path`); это ещё не полное соответствие имени, хеша и сохранённой версии.
Потеря возможности найти или удалить первый квант после Q4 → Q5 **не доказана**:
сценарий на Windows не запускался, нужно проверить все существующие записи и ответ Details.
Если именованный GGUF уже есть в папке/Details, его имя и путь известны даже на Windows;
для определения этого файла не нужны manifest/job. Безопасность удаления общего blob проверяется отдельно.
Q4 → Q5 → удаление Q4 — обычная проверка, не установленный сбой и не повод менять хранение заранее.
Только подтверждённая проблема, мешающая выбранному удалению, требует согласовать узкое исправление.
Новый реестр/индекс/база данных, автоматическая замена ссылок копиями/жёсткими ссылками или перевод на Local этим не разрешены.
Имя файла, похожее на хеш, или один manifest не доказывают принадлежность blob.
Размер файла за ссылкой не равен гарантированно освобождённому физическому месту.
Общие blob, открытые файлы и жёсткие ссылки могут удерживать место; нельзя обещать вымышленные байты.

Одна висячая ссылка на веса не делает модель доступной для запуска.
Другие ошибки чтения объясняются для конкретного места, а не превращают весь список в пустой успех.
Rebuild не должен вернуть выбранную группу из сохранённой версии, уже вошедшей в область удаления.
Эти требования не требуют нового глобального учёта или общего автомата состояний.

## 5. Как это выглядит в интерфейсе

Карточка Cache может по-прежнему объединять данные репозитория.
В Details пользователь сначала выбирает **фактическое место хранения**.
Затем видит отдельные строки GGUF-файлов/семейств и групп частей, с «Удалить» у каждой строки.
Файл `model.gguf` без метки кванта, manifest и job тоже виден и доступен для удаления по имени.
Строки нельзя строить только из `Quantizations[]`: найденный обычный GGUF не должен потеряться.
Состав группы определяется по полным данным: первые 20 файлов не могут быть пределом анализа.
Нормальный сценарий — выбор известных строк, без ручного фильтра или ввода пути.

Подтверждение показывает репозиторий, тип, место, группу и конкретные файлы/части.
Для HF оно явно говорит «во всех сохранённых версиях здесь»; остальные данные останутся.
Повторная отправка блокируется на время операции; сервер всё равно заново проверяет выбор.
Устаревшее содержимое UI не даёт права удалить новый или другой набор файлов.

Занятость, отказ, ошибка чтения и частичный результат показываются простыми словами на месте.
Проблема одного локального места не должна ломать весь список общим HTTP 500.
После операции обновляются тот же Details и список; оставшиеся группы не исчезают из интерфейса.
Сообщение — об удалённой группе, не «репозиторий удалён».
Старый асинхронный ответ не должен закрыть Details другого уже открытого репозитория.
UI остаётся обычным статическим JavaScript в существующем стиле, без новой системы сборки.

Старый DELETE всего репозитория нельзя использовать для кнопки удаления кванта.
Как сохранить совместимость старого API — отдельное решение будущей реализации.
Нельзя молча удалить этот API; если он остаётся, сохраняются проверки его известных опасных случаев.
Но эти случаи не являются основанием сделать удаление кванта рекурсивным удалением папки.

## 6. Когда удаление занято

Нельзя удалять выбранные файлы и затронутые HF-метаданные, пока приложение их меняет.
Учитывается реальный срок изменений: передача, обработка уже скачанного файла (skip),
завершение записи, откат и очистка, а также перестроение ссылок (rebuild) и зеркалирование (mirror),
когда они затрагивают эти данные.
Нужно закрыть промежуток между проверкой занятости и удалением, когда может стартовать новый писатель.
Ответ — «занято», без автоматической отмены загрузки.

Другой локальный квант не считается занятым только из-за общей папки.
Общие HF-метаданные, напротив, могут создать реальный конфликт между группами.
Одной проверки `StatusRunning` недостаточно для перечисленных переходов.
Позднейший явно выбранный Retry или новое скачивание остаются разрешены; вечного запрета нет.

План задаёт результат, а не обязательный механизм блокировки.
Новые leases, RepoState, журнал, карантин и транзакции не являются требованиями.
`copyKey`, `os.Root`, хеши и протокол поколений — возможные детали, не готовые решения этого плана.
Если потребуется новое продуктовое или архитектурное решение вне этих границ, его надо согласовать отдельно.

## 7. Исторический порядок реализации

Список ниже фиксирует первоначальный план, а не текущие незавершённые задачи.
Реализация выполнена в этой ветке; итоговое независимое review ещё ожидает:
1. Подготовить правильную ветку #111 с чистой согласованной базой, сохранив текущую пользовательскую работу. (Выполнено: продолжена существующая локальная ветка `feature/storage-root-ownership`, исходная история сохранена.)
2. Убрать ненужную общую инфраструктуру корней и глобальную переделку чтения;
   восстановить прежнее устранение повторных операций на Windows. (Выполнено в Package 1; удаление всей функции выбора/удаления кванта не заявляется.)
3. Вместе добавить точное чтение места/группы и выбор этой группы в Details.
4. Реализовать локальный путь, включая найденные вручную файлы в `LocalScanDirs` без manifest/job.
5. Реализовать выбранную HF-группу во всех её сохранённых версиях и сохранение общих blob/связей.
   Проверить Q4 → Q5 → удаление Q4 на Windows как обычный сценарий, не предполагая потерю данных о файлах.
   Если подтвердится сбой выбора/удаления, согласовать узкое исправление существующего кода, не новый учёт.
6. Ограничить реальные изменяющие операции, закрыть гонку запуска и проверить безопасность путей.
7. Добавить проверки и обновить `docs/API.md` под подтверждённое удаление в `LocalScanDirs` и новый контракт.
8. Провести независимую интеграционную проверку и review целого результата, не после каждого мелкого коммита.

## 8. Историческая матрица проверок

Эта матрица описывала требуемые сценарии. Часть проверена независимым браузерным
и интеграционным проходом на предыдущем кандидате; она не заменяет проверку
последнего исправления. Нативная Windows/SMB-среда и исчерпывающий набор форматов
не проверялись.

| Случай | Требуемое поведение |
| --- | --- |
| Шесть квантов и второе место | Удалён только выбранный; пять соседей, служебные файлы и второе место сохранены. |
| `LocalScanDirs`, ручной файл | Удаление работает без manifest и job; папка не становится назначением скачивания. |
| Ручной обычный GGUF в стандартной friendly-папке, без HFRepo/manifest/job | Выбранный файл удаляется как локальный; другие кванты и весь HF-кэш неизменны. |
| `model.gguf` без метки кванта, manifest и job | Есть строка по имени и доступная кнопка «Удалить»; исчезает только выбранный файл/известная группа. |
| Split, одинаковый Q, MTP, подпапки, >20 файлов | Выбрана точная полная группа, не все совпадения метки и не обрезанный список. |
| HF: несколько версий, общий blob, прочие связи | Выбранная группа удалена во всех выбранных версиях; нужные другим данные сохранены. |
