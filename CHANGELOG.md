# Changelog

## [Unreleased]

### Added


- Add a service mode: `hfdesk service install|uninstall|start|stop|restart|status` registers HFDesk with the native supervisor of the platform (systemd on Linux, launchd on macOS, the Windows Service Control Manager on Windows). The supervisor owns the lifecycle and HFDesk stays a headless foreground process, the instance resolves deterministic runtime paths of its scope (its own config file, state root and log directory), and it binds loopback by default; exposing it to the network needs an explicit `--listen`. Credentials stay in the service-owned config file and are never written into a supervisor registration (#142).

- A second Windows artifact, `hfdesk-desktop_windows_amd64_v1.3.0.exe`, is now built and published next to the console binary: it is a GUI program without a console window that runs the same HFDesk server in-process behind a notification-area icon and a small Runtime / Logs window showing the server status, the active job count and the live log records. A left click on the icon opens that window, the tray menu offers Open HFDesk, Runtime / Logs and Quit HFDesk (a graceful shutdown), and the host is single-instance per user and session: a second launch detects the running instance and opens the web UI of it. The Runtime / Logs window needs the Microsoft Edge WebView2 Evergreen runtime, and a missing runtime produces an actionable message while the server and the tray keep working. The desktop binary is a separate download and the console binary is unchanged (#141).
- A structured logging pipeline with the new `--log-file` and `--log-level` options: every record carries a level, a timestamp, the component that produced it and structured attributes, the console sink writes to standard error so redirecting standard output keeps working, and the file sink rotates. The desktop host always writes a log file, because a GUI program has no console, and it lands in `<user cache dir>/HFDesk/logs/hfdesk.log` unless `--log-file` names another path (#141).
- Local-only runtime and log endpoints: `GET /api/runtime` reports the version, the status, the URL, the active job counts, the run id of the server and the log cursor, `GET /api/runtime/logs` returns a bounded page of the retained records, `GET /api/runtime/logs/stream` streams them as Server-Sent Events, and `POST /api/runtime/open-logs` and `POST /api/runtime/open-ui` open the log folder and the web UI of the running instance. They take no path and no URL from the caller, and three rules keep them local: the peer address has to be a loopback address, an `Origin` header of another site is rejected, and the `Host` header has to name the local machine, so a name of another site that is pointed at `127.0.0.1` cannot read the runtime data of the local machine. A request that breaks a rule is rejected with `403` and never reaches the handler (#141).
- The requests of the runtime endpoints are written to the log at `debug` level and not at `info` level, so the polling of the Runtime / Logs window (every four seconds) does not fill the bounded log history that the window exists to show. Every other request keeps the `info` level, including a request that answers with an error (#141).

- Add a read-only Community feature for repository Discussions and Pull Requests: `GET /api/community/{owner}/{repo}` lists both types with paging and type/status filters, while `?num=N` returns a thread with sanitized comments and human-readable event summaries. The Model Details view now has Overview and Community tabs; the read-only Community tab is lazy-loaded, lists Discussions and Pull Requests, opens a thread with comments and events, and supports model and dataset repositories. The proxy uses the configured endpoint, proxy, and HF token without exposing the token to the browser (#136).
- Report gated Hugging Face repositories as a dedicated access state instead of a partial analysis: the API returns HTTP 403 with error code `gated_repo`, the repository type, an accept link for the configured endpoint, and boolean-only token state, and the Model Details view shows configured-token and repository-agreement guidance without exposing the token.
- Model Details now opens README, lineage, and related-download repository links in-place, with Back/Forward history across models, datasets, and revisions (#135).
- Opt-in local-I/O benchmark for multipart finalization (`go test -bench BenchmarkRangedFinalization ./pkg/hfdownloader/`) recording total staging bytes written (including the transfer landing on disk), extra local payload writes beyond one file size, full-file hash bytes read, and the network-complete → file-done elapsed time: `Verify=size` shows ≈0×S extra local payload writes and no hash reread, `Verify=sha256` ≈1×S hash read (#140).

### Changed

- Multipart downloads write ranged workers directly into one preallocated staging file at their assigned offsets instead of downloading `.part-NN` payload files and stitching them with a full-file assembly copy (#140). In HF cache mode an LFS blob stages as `blobs/<sha256>.incomplete` — the future blob itself — so finalization is an atomic rename plus snapshot/friendly link work with no payload-sized copy; other destinations use `<destination>.incomplete`. Resume state persists as versioned per-range committed-prefix metadata next to the staging file and is authoritative for an existing incomplete download, but only when it is provable: the record must match the resolved commit, repo, path and size, its blob SHA must be present on both sides or neither, its ranges must tile the file with normalized completion (`Done` exactly when the range is fully committed), and the staging payload must exist at the expected logical size before any create/truncate. An interrupted transfer resumes from its durable high-water marks, and changing the connection count between runs re-fetches only the missing bytes instead of invalidating valid ones. The claim record is heartbeated through transfers, retry/`Retry-After` waits, strict hash verification and finalization; unreadable or ambiguous legacy records are preserved rather than treated as stale, and identity-mismatched current records are discarded only under lifetime ownership. Ownership uses a random per-process instance token plus heartbeat freshness and a real same-host liveness check (with a Windows `OpenProcess` implementation), so PID reuse and containers sharing PID 1 cannot be mistaken for self-ownership; the record remains the resume/identity state. Exclusion is fenced by an OS-level exclusive lock on the persistent sibling `<staging>.lock` (`flock(LOCK_EX|LOCK_NB)` on Unix, an exclusive-share `CreateFile` handle on Windows), acquired before the claim transition and held for the whole ownership interval — claim read, create/resume, transfer, hash, publish/cleanup. A busy lock is a live owner, including a suspended process that stopped heartbeating but could still resume writing through an open handle; a crashed process releases the lock at death, so takeover/resume is immediate, and there is deliberately no takeover while a suspended owner is alive (terminate it to recover). Every staging-record transition is serialized locally by a per-path metadata gate while the lifetime OS lock excludes current-version foreign mutators, and re-reads claim identity so a heartbeat cannot resurrect a lost claim; a claimant that loses never skips the file: the file is not present while the live owner holds it, so the download path waits for the blob key's ownership domain and re-checks the published content-addressed target (see the job-contract entry under Fixed). Publish re-reads the record under that lock and verifies the OS lock is still held before the rename; a missing or foreign record is refused with `errStagingClaimLost` and the staging file is left for its actual owner. Platforms/filesystems unable to provide the lifetime OS lock return an operation error before claim/payload mutation and preserve existing partials; this is runtime failure handling, not permanent support policy. The lock file is never unlinked and is excluded from cache statistics and cleanup. Completion is content-addressed: an existing publish target proves completion only when it is `blobs/<known-sha>`; an arbitrary legacy/output destination or `tmp-<sha>` staging name follows the pre-download skip decision and is downloaded again and atomically renamed over when that decision declined it (so "blob exists" is reported only for a published blob-keyed target). Progress is reported from in-memory byte counters instead of re-statting part files on every tick. Every ranged response is strictly validated (exact `Content-Range` match, advertised total, exact body byte count, bounded writes) before any byte is written. Cleanup never removes a staging pair while another live claim remains, and re-checks that under the same per-path metadata gate. Valid legacy `.part-NN`/`.parts.json` partials are migrated into the staging file once and the obsolete artifacts are removed only after the migrated layout is durable, and a leftover single `<destination>.part` is migrated as a sequential prefix when no usable multipart layout exists; an oversized single `.part` is discarded rather than clamped, and migrated bytes are content-proven before publication as described for `Verify`.
- `Settings.Verify` now actually controls LFS verification (deliberate semantics change, #140): `none` performs no post-download content hash; `size` (the default) checks the exact expected size and complete validated transfer coverage on both the ranged and single-request paths and performs no full-file SHA-256 reread on the normal transfer path — the pre-download skip check over an already-present destination, the one-time legacy-migration content proof, and the inherited single-path `.part` proof may still hash; `sha256` verifies the full content against the known digest with at most one full-file read, always before publication when a known digest exists — only an eligible fresh sequential LFS ranged transfer with one task covering the whole file hashes while writing, every other transfer (including the single-request path) performs one sequential pass before the rename, a mismatch never publishes corrupt bytes, and the untrustworthy staging data is discarded so a retry re-downloads from scratch; `etag` proves a known SHA-256 digest with that same single pre-publication pass (so a mismatch never reaches `blobs/<sha>` or the destination) while non-LFS ETag-only files keep the historical no-post-check behavior; when `sha256` has no known digest, the HEAD-ETag fallback can report a mismatch only after publication. Bytes migrated from a pre-#140 partial are tagged `LegacyMigrated` and content-proven with one full-file SHA-256 pass before publication whenever the item has a known digest and `verify` is not `none` (the explicit one-time migration exception, even in `size` mode); with `none` they inherit that mode's no-hash semantics. The single-request path is under the same trust model: a `.part` is a sequential prefix with no range-layout record - it is identified by the `<dst>.part.meta` sidecar, not by a per-range layout - so every 206 must match the exact requested `Content-Range`, expected total and body length, writes are bounded to the requested range, the on-disk size must be exact before the rename, and a known digest is proven with one full-file pass before the rename in `sha256`/`etag` modes (inherited `.part` bytes are also proven once in `size` mode, and a known digest with an unknown expected size is proven because only the digest can validate the stream); a partial with no known expected size is never resumed, and a mismatch never publishes. A multipart staging record also carries a durable `ProofPending` gate: it is set and flushed before any known-digest proof starts and cleared and flushed only after the proof succeeds, and on resume it forces the proof in every mode except `none` (including `size`) when a known digest exists, so a crash mid-proof, a failed mismatch cleanup, or a later mode change cannot publish unproven all-Done ranges; a mismatch keeps the flag set, attempts poison (truncate to zero) only while the claim is still owned under the per-path metadata gate, and attempts the owned discard; if ownership cannot be verified the durable flag remains the guard, and publication is refused while a known digest's proof is pending. `none` is the explicit no-hash opt-out. The `hfdownloader` package docs, the `Settings.Verify` comment, and the settings UI label describe the new semantics.
- `hfdownloader.PlanRepo` and `hfdownloader.Download` now reject a path-shaped filter combined with `AppendFilterSubdir` (typed `ErrAppendFilterSubdirPathFilter`) before any network or plan work: only single-component group/token filters can name a destination subdirectory. Path filters remain valid with `AppendFilterSubdir` disabled.
- README rendering and Hugging Face repository-link classification now have a single Go implementation: the bundled UI renders the server-sanitized `html` from `GET /api/readme` and no longer carries a client Markdown renderer or duplicate URL classifier (#135, #147).
- Remote repository tree paths must now use their canonical spelling: a raw path whose `path.Clean` form differs (for example a `./` segment, duplicate slash, or trailing slash) fails planning with a non-canonical-path error instead of being normalized, so two spellings of one remote file cannot both be planned and race to write a single cache entry.

### Fixed

- A staging record whose owner cannot be proven alive or dead is no longer reported as "another live writer" (`#140`). A blob-keyed staging record written without the lifetime OS lock fence (`LockFenced` is false, which no released version ever wrote) or one that cannot be read or parsed is refused by the claim, and the refusal surfaced through the same sentinel and the same message as a PROVEN live owner: the operator was told "blob <sha> is being downloaded by another process; try again later" for a state where no live writer was proven to exist, and no automatic recovery was attempted. The refusal itself is unchanged - the conservative, owner-decided rule still holds, and the record and its partial are preserved and never taken over (no age-based takeover, no takeover without proof of same-host death). What changed is the reporting: the unproven record now says that its staging state "cannot be proven to belong to a live or dead owner (legacy or unreadable record)", that the partial is preserved, and that removing the staging pair is the recovery, and it carries the new exported `hfdownloader.ErrStagingOwnershipUnproven` sentinel, so a caller can tell it apart from the proven live owner with `errors.Is`. The proven live owner keeps its transient "blob <sha> is being downloaded by another process; try again later" message, and a provably dead owner is still resumed. The operator procedure is documented (in `AGENTS.md`, the `hfdownloader` package docs and `docs/API.md`): remove the staging pair (`<staging>` and `<staging>.meta`, for example `blobs/<sha>.incomplete` and `blobs/<sha>.incomplete.meta`) and retry the download; the item then starts from zero. The persistent `<staging>.lock` is never removed, and a staging pair whose owner is a proven live owner is never removed either.
- The ranged publication now asserts the "never publish an incomplete payload" invariant instead of relying on the control flow that reaches it (`#140`). The guarantee was correct but implicit: every range worker's nil return was caught by the cancellation guard or by the error drain, so a future refactor of that path could have broken it silently. Before the rename, the publication now checks that the range layout covers the whole expected payload - every range `Done` and the committed total equal to the expected size, in both the live layout of the download and the persisted claim record, using the package's own range validation. An incomplete layout is refused with the new `errStagingLayoutIncomplete` error and nothing is renamed, so the staged bytes stay on disk for a resume; a complete layout publishes exactly as before.
- The single-request path now inherits staged bytes only under a proven identity (`#140`). For an item without a known digest the staging name is derived from the item's path (`tmp-<sanitized path>`), so two different objects - or two revisions of one object - share one staging name, and the destination's ownership domain excludes concurrent writers without establishing WHICH object the staged bytes belong to: a `.part` was resumed from its size alone, so a partial left by another file or another revision could be published (at `verify=size` a mixture of two objects' bytes, and with no HTTP request at all when the inherited size already equalled the expected size). A versioned sidecar `<dst>.part.meta` now records the repository, the resolved commit, the item's relative path, the expected size and whether that commit was actually resolved (pinned). Bytes already on disk are inherited only when that record exists, is readable and well-formed, matches the current item exactly and is pinned on both sides; otherwise the inherited bytes are discarded and the transfer restarts from zero, so unproven bytes are never published. An unresolved commit (the planner's fallback to the requested revision) pins nothing, so nothing is inherited from it. The record is written before any inherited byte is trusted, is removed together with the partial it describes (on publication and in the cancel-cleanup path) and survives an interrupted run, which is what makes the next run's decision possible; a legacy `.part` without a record is never inherited. The known-digest content proof is unchanged and still applies to the inherited bytes.
- The ranged staging path now inherits staged bytes only under a pinned identity, the same rule the single-request path already applied (`#140`). The ranged claim record carried the repository, the resolved commit, the item's relative path and the expected size, and its trust decision compared the commit STRING alone: a record written under an UNRESOLVED revision (the planner's fallback to the requested branch name, which pins nothing) was accepted whenever the string matched, the size matched and the blob SHA was absent on both sides. For an item without a known digest - which the planner permits - there is no content proof either, so in the default `verify=size` mode the bytes an earlier run of a moved branch staged could be published as the new revision's content. The record now also states whether its commit was actually resolved (`commit_pinned`), and a record is resumable only when the identity is PINNED on both sides (the record's own flag and the current plan's) in addition to the repository, commit, path and size match, the blob SHA both-or-neither rule and the range-layout validation. A record written without the flag is unpinned and therefore not inheritable, which is the safe direction; no released version ever wrote these records. A pinned, matching record keeps its resume exactly as before: only the missing bytes are re-fetched.
- The cache surfaces and the mirror now separate published content from the downloader's staging artifacts with one exhaustive classification (`#140`). The old suffix blacklist knew only `.incomplete`, `.meta`, `.meta.tmp` and `.lock`, so an unfinished single download (`blobs/tmp-<name>`, `blobs/tmp-<name>.part`) and a legacy multipart residue (`<sha>.part-00`, `<sha>.parts.json`) were counted as ready content, listed as cached files, seen by the cache selection and copied by a mirror. The classifier now covers every producer the downloader creates - the single-request staging name with its `.part` and its `.part.meta` identity sidecar, the ranged staging pair with its atomic record temp, the persistent ownership locks, the legacy multipart family, the flat-mode partials and the cache store's atomic copy temp - and a published blob is recognized positively as a canonical 64-hex digest. A file in `blobs/` that is neither a staging artifact nor a canonical digest is an unusual published name (the public storage API accepts such names): it stays content, so the cache statistics count it, the listing shows it, the selection sees it, the mirror copies and verifies it, and the deletion path may delete it. The classification is by name shape, so a `blobs/` name that CARRIES a staging shape (`tmp-<name>`, `<name>.part`, `<name>.part.meta`, `<name>.lock`, `<name>.incomplete`, `<name>.incomplete.meta`, `<name>.meta.tmp`, `<name>.part-NN`, `<name>.parts.json` or `<name>.tmp-<random>`) is treated as a staging artifact by every surface, including the deletion path - the conservative choice: a staging artifact is never deleted - even when such a name was published content. A canonical 64-hex blob is unaffected: it is content, and the deletion path may remove it. The exclusion applies inside `blobs/` only, so a legitimate `*.meta` (or `*.part`, `*.lock`) file outside that namespace - a snapshot entry, for example - is content; the mirror now copies AND verifies it, because the verification used to walk `blobs/` only and never checked the snapshot entries it had copied. Copy and verification therefore always agree on the same set.
- Every cache destination now owns an ownership domain, not only the content-addressed ones (`#140`). The writer of a destination and the cleanup of that destination now agree on ONE domain identity: destination `blobs/tmp-<name>` means domain key `blobs/<name>` and domain lock `blobs/tmp-<name>.lock`. For a content-addressed item the name is the SHA-256, so the domain is exactly the blob key's domain of before (key `blobs/<sha>`, lock `blobs/tmp-<sha>.lock`) and the publication's `holdsBlobKey` check is unchanged. An item WITHOUT a known digest (the planner allows an empty SHA-256) got a path-derived destination (`blobs/tmp-<sanitized-relative-path>`) that NO writer ever held: two writers of that destination were not mutually excluded — in this process or in another one — and the cleanup's protection was vacuous, because it derived the same key while nobody held it, so cancelling a job could delete another live job's `.part`/temp for the same path. A writer of such a destination now holds its domain for the whole operation, so a second writer waits for it (bounded, context-aware, never a takeover) and the cleanup of that destination leaves a live writer's artifacts alone. A path-derived destination has no published content-addressed target to re-check — its bytes are moved into a blob whose name is the digest computed at store time, which the waiting writer cannot know before it transfers the file — so after it waited for the domain the item OBTAINS the file itself: it re-downloads these small non-LFS files, and the store then reuses the already published blob instead of replacing it. A successful skip that leaves the file missing remains forbidden. A writer that cannot take its domain fails the item before it writes any payload, exactly like the content-addressed case, and the partial data of an earlier run is preserved. The legacy/output (flat) mode has no destination domain: that namespace has no internal `blobs/`-style identity, so it has no destination-domain key and no destination-domain lock file, and the wait-and-re-check protocol does not apply there. It is not lock-free, though: the multipart route stages at `<destination>.incomplete` and takes the lifetime OS ownership lock on the persistent sibling `<destination>.incomplete.lock` — a zero-byte artifact next to the user's model file, never unlinked — so a concurrent second writer of the same flat destination on that route is excluded and fails its item with the actionable live-owner error ("blob <sha> is being downloaded by another process; try again later") instead of racing. That is safer than the pre-#140 behavior, where two processes wrote the same `.part-NN` payload files and could publish a silently corrupt model. The single-request route is not excluded: it creates no lock artifact next to the destination (only `<destination>.part`, removed on success) and takes no ownership lock, so two writers of the same flat destination on that route still race over the same `.part`.
- A link-creation failure now fails the item in the skip paths too, instead of only in the transfer path (`#140`). A cached file is reachable through its snapshot entry and its friendly entry; the payload in `blobs/` alone is not the requested path. The pre-download "blob exists" skip and the post-domain "blob exists" skip ignored the error of the link creation, so the item reported `file_done` and the job reported success while the requested path was not reachable at all — the transfer path already treated the same failure as fatal for the item, so the two paths disagreed inside one contract. Both skip paths now fail the item with an actionable error ("the file is in the cache but its cache path is not reachable", distinguishable with `errors.Is` through the new `hfdownloader.ErrCacheLinkUnreachable` sentinel) and emit no `file_done` success, and the end-of-job reconciliation that re-creates the links of skipped items surfaces its link failures as a job error instead of only a warning, so a job cannot finish successful with a missing path. "Job completed successfully" therefore means the requested files are present AND reachable at their snapshot/friendly paths. The friendly entry is deliberately absent when the friendly view is disabled, so that is not an error. The transfer paths create the cache entries through the same helper, so a link-creation failure carries the same `ErrCacheLinkUnreachable` sentinel there too and the item fails identically on every path that creates the entries.
- A download job no longer reports success while a requested file is missing because another writer owns it (`#140`). "Job completed successfully" now means the requested files are present: a file owned by another live writer is not present, so it is never a successful skip. When the blob key's ownership domain (`blobs/tmp-<sha>.lock` plus the in-process slot) is held by a proven live owner — another process, or another writer of this process — the item WAITS for the domain (bounded, context-aware, never a takeover) and, once it holds the domain, RE-CHECKS the published content-addressed target: a blob the owner published while the item waited is reused, the item finishes as an ordinary "blob exists" skip with its own snapshot and friendly entries created and without a second transfer; an owner that released the domain without publishing makes this writer download the file itself; and a live owner that still holds the domain when the wait budget expires makes the item fail with an explicit, actionable error ("blob <sha> is being downloaded by another process; try again later") instead of a false success. The re-check trusts the EXISTENCE of the published content-addressed blob as completion proof, exactly like the pre-existing "blob exists" skip does, and does not re-verify its content: in `size` mode a torn blob written by a foreign writer is therefore accepted as complete, the same content-addressed assumption the pre-existing skip already makes. The wait budget is a package-level knob derived from the existing ownership-lock convention — 60 times the 5s acquisition window, so the effective budget is 5 minutes — and it is not a user setting; the in-process wait is bounded by the job's context only, and cancellation stays prompt. The wait runs INSIDE the item's goroutine, and the item already holds its `MaxActiveDownloads` slot, so a waiting item occupies a download slot for up to those 5 minutes: a job whose item waits for a foreign owner can look stalled, and it holds a concurrency slot it is not transferring with. What the operator sees: the item stays in progress (no progress events are emitted while it waits, so its byte counter does not move), and when the budget expires the item fails with the actionable error above and the job's status is failed, not completed. The existing "blob exists" skip (the file IS present) and the existing unknown-ownership error (`BlobOwnershipUnknown`) are unchanged.
- The cleanup of a blob key's artifacts now participates in the same ownership protocol (`#140`). `CleanupJobPartFiles` removed the `blobs/tmp-<sha>` staging name, its single-request `.part`, the legacy `.part-NN` parts and the blob-keyed staging pair (`blobs/<sha>.incomplete` and its `.meta`) directly, with no check of the blob key's ownership domain, so cancelling a paused job whose key meanwhile became owned by another live job deleted that job's LIVE partial: the other writer kept filling an unlinked inode and its later publication failed with ENOENT. Those artifacts are now removed only while the key's ownership domain is held; when a live owner holds the key — in this process or in another one — the artifacts are left alone and the contention is reported. A job can still clean up its own artifacts: its writer releases the domain when it returns, and the downloader's own cancel cleanup removes its staging while it still holds the domain. The residual limitation: the cleanup cannot tell "my own key" from "another live owner of the same key" beyond the domain itself, so a key another writer owns is left alone (the safe choice) even when the cancelling job also had bytes for it. A legacy/output-mode destination is not blob-key-scoped and has no destination domain to hold: that namespace has no internal `blobs/`-style identity. Its cleanup is claim-checked instead: the versioned staging pair (`<destination>.incomplete` and its `.meta`) is removed only while no live claim remains, and the single `.part`, the legacy `.part-NN` parts and `.parts.json` are removed as before; the persistent `<destination>.incomplete.lock` of the multipart route is never unlinked.
- A proxy URL without a host leaked its password: a proxy URL of the shape `http://user:password` is read by a parser as the host `user` with the port `password`, and the parse failure of that URL quotes the port, so the reason of a proxy configuration failure carried the proxy password into the log records and into the error response of `GET /api/search`, which is not served to loopback clients only. The reason of a proxy failure now names the cause of the failure without quoting any part of the URL that could be a credential, and the human readable proxy description drops the userinfo of the URL and the separately configured credentials as well. A normal proxy URL still reports its host and its port, so a misconfiguration stays visible (#141).
- The cache status check no longer reports an unknown ownership state as "downloading by another process" (`#140`). `CheckBlob` distinguishes three outcomes: a proven live owner is `BlobDownloading` (the item must NOT be skipped: the file is not present while that owner holds the key, so the item waits for the blob key's ownership domain and re-checks the published target — see the job-contract entry under Fixed), a provably dead owner is `BlobStale` (the item may be resumed), and an unknown ownership state — the OS-level ownership probe failed (for example `EACCES` on the lock file) or the platform cannot represent the lock — is the new `BlobOwnershipUnknown` status together with an error wrapping the new `ErrBlobOwnershipUnknown` sentinel. The downloader surfaces that error instead of skipping the item: the previous behavior reported "download complete (downloaded 0, skipped 1)" while the blob was still absent and the partial was untouched. The incomplete payload is preserved, and the existing status values keep their meanings.
- The publication of a content-addressed blob no longer overclaims what it guarantees, and the exported `FinalizeBlob` no longer replaces a published blob (`#140`). Three corrections: the hard-link-unsupported branch of the publication used to be a stat-then-rename — and `os.Rename` REPLACES an existing target on Unix and on Windows — so a target that appeared between the stat and the rename was replaced, while the documentation claimed the fallback "still refuses to replace an existing target"; the fallback is now a domain-exclusive placement that runs only while the ownership domain of the blob key it publishes is held, and it refuses to run at all without that domain, so an existing `blobs/<sha>` is never replaced by a domain participant and the weaker guarantee is never reached by accident (hard-link support stays no prerequisite for downloading). `FinalizeBlob`, an exported writer of `blobs/<sha>`, renamed over the target with no domain and no no-replace primitive, so it replaced a blob another writer had already published; it now participates in the blob key's ownership domain and publishes through the same no-replace primitive, and an existing blob is kept while the call reports the conflict. The single-request route also failed late when the lifetime ownership of the blob key was unavailable: it transferred the file, wrote the payload and only failed at the store step, which also removed the partial; the domain is now acquired before the transfer, so the operation fails before it writes a payload and an earlier run's partial is preserved. The Go standard library exposes no atomic no-replace rename on any supported platform — `os.Rename` replaces on Unix and on Windows, and `syscall` exports neither `renameat2(RENAME_NOREPLACE)` nor `renamex_np(RENAME_EXCL)` — so the atomic no-replace tier is the hard link, and the fallback tier is domain-exclusive; the mirror writer and the selected-GGUF delete path remain the documented writers that take no domain.
- A content-addressed blob key now has ONE publication domain shared by every route that writes it, instead of one private domain per staging path (`#140`). The ranged route (`blobs/<sha>.incomplete` → `blobs/<sha>`) and the single-request route (`blobs/tmp-<sha>.part` → the cache store → `blobs/<sha>`) used to be able to write the same key at the same time: both could decide that the blob did not exist yet and then place their own bytes, so the second placement replaced the first writer's blob with bytes that do not hash to the key they are stored under — a corruption `CheckBlob` then reported as complete — and the ranged route could adopt the single route's LIVE partial as a pre-#140 leftover, publish a mixture of two writers' byte streams under the content-addressed name and delete the partial the other writer was still filling. Both routes now hold the same domain (an in-process slot keyed by the blob key plus the lifetime OS lock on the persistent sibling `blobs/tmp-<sha>.lock`, which is never unlinked and is excluded from cache statistics, listings, mirrors and cache deletion), so a live partial of one route is never adopted, migrated or deleted by the other, and the publication decision and the placement that follows it cannot be overtaken. The publication itself has two tiers, chosen by the FILESYSTEM. On a filesystem that can create hard links it is a single atomic no-replace step (a hard link, which fails when the name exists), so an existing `blobs/<sha>` is never replaced by another writer's bytes, proven or not, and the normal path stays rename-only in cost. The Go standard library exposes no atomic no-replace rename on any supported platform — `os.Rename` replaces an existing target on Unix and on Windows, and the `syscall` package exports neither `renameat2(RENAME_NOREPLACE)` nor `renamex_np(RENAME_EXCL)` — so on a filesystem WITHOUT hard links the placement is a check-then-rename performed while the blob key's ownership domain is held exclusively: there an existing `blobs/<sha>` is never replaced by a DOMAIN PARTICIPANT, and a writer outside the domain is not fenced by it. That placement refuses to run without the ownership domain of the blob key it publishes, so the weaker guarantee is never reached by accident, and hard-link support remains no prerequisite for downloading. Known limitation, documented rather than fixed: the mirror writer copies destination blobs with a non-atomic truncate-and-write and a size-only check, and the selected-GGUF delete path removes blob payloads; neither takes the blob key's ownership domain, so neither is fenced by it, and the downloader's publication invariant does not depend on them.
- Correction to the #140 ownership follow-up: shared staging mutations require the supported lifetime OS lock; unsupported, denied, or failed acquisition now returns an operation error before claim/payload mutation and preserves partial data. There is no lease-only mutation fallback. Legacy/unfenced records are retained unless same-host owner death is proven. In-process record transitions use a per-path metadata gate; transition age never authorizes breaking or unlinking a holder's critical section. Cancellation while waiting to publish is observed before rename.
- Ranged body completion now requires clean framing/EOF in addition to receiving the requested bytes. If a transport/stall error occurs after the final byte was written, the final byte remains uncommitted and is re-requested as a nonempty range; it is never marked Done or published from that failed response. Range-record version 3 marks Done only after clean body framing; version-2 Done checkpoints migrate by preserving their prefix and revalidating the final byte. Fresh claim JSON is atomically installed without replacing an appeared record, and a failed takeover replacement preserves the validated predecessor until a complete replacement is ready. The claim record no longer requires hard-link support: the complete record is staged in a fresh file and installed by an atomic hard link, falling back to an atomic rename on a filesystem that cannot create hard links, so a ranged download still succeeds there. The staged copy is always a fresh inode, so a staged path left behind by an interrupted install — which may share the authoritative record's inode — is never written through and can no longer empty the authoritative record before it is replaced.
- Single-path finalization now checks cancellation after `file_finalizing` and again immediately before rename, applying existing pause-preserve versus explicit-cancel cleanup. Unknown-size LFS items that fall back from multipart to single-path are stored through the cache store owner, creating the blob and its snapshot/friendly entries instead of leaving a dangling direct-publish assumption.
- Ranged-download staging now follows one explicit trust model (#140): an existing arbitrary destination is never completion proof (only a content-addressed `blobs/<known-sha>` is); legacy `.part-NN`/`.parts.json` or single-`.part` bytes are content-proven with one SHA-256 pass before publication when a digest is known and `verify` is not `none`, and an oversized single `.part` is discarded instead of clamped; every staging-record transition is serialized locally by a per-path metadata gate under the lifetime OS lock so concurrent take-overs cannot produce two writers or delete the winner's claim; and every post-claim phase, including the legacy migration copy and the strict hash, is cancellation-aware with the same claim-checked cleanup semantics. A moved commit is caught by the content proof (identity alone cannot prove the old bytes match). The single-request path now follows the same model (strict 206 validation, bounded writes, exact on-disk size, and a pre-publication one-pass proof of a known digest for fresh and inherited bytes in `sha256`/`etag`, with inherited bytes also proven in `size`), publish refuses a missing/foreign claim, and a whole-interval OS ownership lock fences in-flight writes that the record lease could not; a multipart layout with no usable part falls back to a valid single `.part` instead of deleting it, and an oversized ranged body no longer poisons the strict hash-on-write state (the retry falls back to exactly one final full-file pass) or double-counts progress. A known-digest mismatch whose owned cleanup fails logs that failure and leaves a durable `ProofPending` record, so a later `size` run cannot publish the corrupt staging with zero ranged GETs; poison (a zero-length payload) is attempted only while the claim is still owned under the per-path metadata gate, so a stale writer cannot truncate another owner's staging, and the pending flag is cleared durably only after a successful proof, immediately before publication.
- Publish no longer overwrites a content-addressed blob that another writer completed while a transfer was in flight: the publication places the payload with a no-replace primitive, so an existing `blobs/<known-sha>` is completion proof and keeps its bytes — the losing writer discards its own staging pair and reports the item as complete (`#140`). The "the blob does not exist yet" decision and the placement that follows it are one step — atomic no-replace on a filesystem with hard links, domain-exclusive on one without, see the publication-domain entry above — so a concurrent publisher can no longer be overtaken between them. A record written while holding the OS ownership lock now persists that mode (`LockFenced`), so `CheckBlob` treats a free ownership lock as authoritative and reports a resumable crash state as stale instead of "downloading" when the recorded PID happens to be reused/live; unfenced legacy records remain protected unless same-host owner death is proven. Mismatch poison is performed only while the claim is still owned under the per-path metadata gate, so an unfenced stale writer cannot truncate another owner's staging. The single path retries a nonempty final-byte range when response framing fails after all requested bytes arrive; it does not publish until framing is clean. It emits `file_finalizing` before the pre-publish proof (and a full-progress reading for an exact-size inherited partial), removes obsolete legacy multipart artifacts on success, and proves a known digest with an unknown expected size. The ownership probe takes a non-owning shared lock, so concurrent probes are never mistaken for a writer. Skipped same-SHA/different-path items are reconciled after all files finish and get their own snapshot/friendly entries. Staging `.meta.tmp` files and the persistent locks are excluded from cache listings/stats/selection and mirrored content, the single-path size check stats the actual verify target, and mirrors skip all staging artifacts.
- A legacy/unfenced staging record (`LockFenced` absent/false) is preserved unless same-host process evidence proves its owner dead; age or ambiguous identity does not prove that an older writer cannot resume. Existing multipart resume state (a valid v2 pair, the blob-keyed LFS pair, or a usable pre-#140 `.part-NN`/`.parts.json` layout) now keeps the multipart route for a ranged-capable item regardless of `MultipartThreshold`, so a threshold change no longer ignores and deletes valid state; without range support the downloader emits an explicit warning, downloads the full file through the single path, and removes the obsolete v2 pair only after the final file is durable (claim-checked), while the legacy family is removed by the single-path success cleanup. An ignored-Range `200` restart now clears the inherited-bytes flag, so `Verify=size` does not perform an unnecessary full SHA proof on the restarted transfer.
- Cache selection now exposes a downloaded mmproj companion as its own deletable group instead of dropping it from the selectable model: `GET /api/cache-selection` reports a group `kind` of `llm` or `vision_encoder`, a companion group carries an `mmproj-` group id and no model-quantization label, and the Model Details view renders a distinct "Vision encoder" badge with its own Delete action. The delete confirmation names the vision-encoder role in both the local and the HF case and never claims the selected artifact class remains. Deleting a companion removes only that companion, deleting an LLM group never removes a companion, coexisting F16/BF16/F32 companions stay independently selectable and deletable, and the existing writer, snapshot, and identity-pinning protections still apply (#138).
- The artifact-role rule for multimodal projector companions now has a single owner in `pkg/smartdl` (`IsMMProjFile`, the previously unexported helper), which the download picker, the cache metadata, and the cache-selection model all use. The rule is a case-insensitive "mmproj" match anywhere in the file's basename, so a dot-separated companion (`model.mmproj-f16.gguf`) and a name that merely starts with "mmproj" (`mmprojector-f16.gguf`) are both companions. `GET /api/cache/{owner}/{repo}` therefore reports a dot-separated companion under `hasMMProj`/`mmprojFiles` instead of listing it as an `F16` quantization, and a repository whose only companion is dot-separated now also reports the `vision` capability; the cache selection reports a companion as a `vision_encoder` group instead of a model quantization (#138).
- `GET /api/analyze` now supports an explicit `type=model|dataset` selector, so a repository that exists as both namespaces resolves without repeating the type-selection prompt (#135). `type` takes precedence over the legacy `dataset` parameter, and `type=model` combined with `dataset=true` is rejected as a conflict. The legacy `dataset` parameter keeps its pre-#135 behavior: only `dataset=true` forces the dataset namespace, while `dataset=false` still auto-detects.
- The Model Details `HF Hub ↗` action now uses the endpoint reported by `GET /api/health` when settings have not loaded or the settings fetch failed, and stays hidden rather than guessing `huggingface.co`; health now reports the normalized effective `endpoint` (#135).
- Filtered plan/download scans no longer succeed when no non-excluded path directly matches and no recognized dataset membership selects data: `POST /api/plan` now returns `400` with error code `no_filter_match` instead of a metadata-only plan, while empty repositories without filters still plan successfully.
