### Added

- The Windows desktop can work as a tray companion beside an installed service — without running its own server — and after an installation it restarts as exactly that.

Tray-companion mode starts no server and listens on nothing: it is a companion to the service that already runs. Its menu opens the service's web interface, its window shows the tail of the service log and can open the whole file, and Exit closes only the companion — the service keeps running. A finished installation restarts the desktop host as this companion.

- The service update report names the old program file left behind when the registration moved to another file and offers to delete it with one press; nothing is removed automatically.

An update that moved the registration to a different program file leaves the previous one on disk. The report names it and offers **Delete the old file**, which never runs on its own. Nothing is deleted without that press.

### Changed

- The tray menu's state line names the state of the Windows service in words — `Service: not installed`, `Service: installed`, `Service: running`, `Service: starting`, `Service: stopping`, `Service: unknown`.
- The Logs window badge only says whether the service is installed — `Service: installed`, `Service: not installed`, `Service: unknown`.
- The service status in the tray and in the window follows every reading of the service, keeping both surfaces on the real state.

The state comes from one owner and each surface follows every reading, so the tray and the window cannot drift apart or keep an old answer. The badge keeps to what it can prove — installed or not — while the tray line also reports running, starting and stopping, and says unknown when the state could not be read.

- The tray menu adds Start service, Stop service, Update service and Delete service, and deleting removes only the registration, keeping all data.
- Everything about the service now lives in one **Service** submenu with its status line at the top: the duplicate **Service…** item is gone, and **Install service…** shows only where there is nothing to install.

The menu root is Open HFDesk, Logs, Service and Quit, with every service action inside the **Service** submenu beside its state line. One action runs at a time, deleting asks for confirmation first, and the status is refreshed afterwards; deleting takes down the registration only, keeping all data. **Install service…** appears only while there is nothing registered for it to replace, and the separate dialog entry that duplicated it is gone.

- One **Logs** window replaces the separate Runtime / Logs window in both desktop and tray-companion mode: the live log while the address answers, and an honest state with actions when it does not.
- The Logs window and the error windows open their log file with one action instead of showing its path as text.
- When the address does not answer, the Logs window also offers the step that fits the state — **Start service** for a registered service that does not run, **Install service…** when none is installed.

There is one Logs window now, in both modes, showing the live log page of the running service while the address answers. When it does not, the window says so, states the facts it knows and offers the step that fits — that step runs the same flow as the tray item, and the window re-reads the state afterwards. The log file opens by one action rather than showing its path as text, and that action runs in the window's own process, which is also what makes it work beside a service: the server side cannot open anything in the signed-in session.

- The notice about the missing service program says in one short line which file is needed and where, and keeps its actions — the download and the manual route — visible side by side.
- Error reports now name the log file of the launch they belong to.
- Window texts are now short and plain: the facts of what happened, and a next step only where a failed action has to name one.

Dialogs name the facts, and a next step only where a failed action has to name one: failure windows name the log file of the launch they belong to, so a report and the file it points at match, and one step follows. Reports of a finished action say only what happened — the program, the address, the state and the data directory — and stop there; an invitation to open the address or install again belongs to a window that asks a question or reports a failure. Where a line had been cut too far, the facts a window needs came back short: the program and account an installation tried to register, the name of the missing program, the reason an image cannot run.

- Installing from a removable or network drive now warns that Windows may start the service before the drive is ready.
- The install confirmation is cut to the question and two short fact lines — the service starts at boot and keeps running, and its data is separate — with the removable-drive warning as its own line.

The installation confirmation is now the question and two short fact lines. Installing from a removable or network drive adds its own line: Windows may start the service before that drive is ready, so the program would not be there yet. The facts the dialog no longer carries live where they matter, in the download dialog.

### Fixed

- The Logs page a browser loads from a running Windows service now reports `Service: installed` instead of `Service: unknown`: the page served by the instance reads the state of the registration the instance runs from, and its install action stays unavailable.
- The service log under `%ProgramData%` can be read from the Logs window again: at every start the instance grants interactive users read access to its own log directory and active log file, and touches no other descriptor.

The page served by the instance reads the state of the registration that instance runs from, bounded so an unresponsive supervisor cannot hold the page; a host that is the service cannot install it, so that action stays unavailable there. The log itself is readable again: at every start the instance grants signed-in users read access to its own log directory and active log file, and only where the descriptor is exactly the factory one — anything wider or foreign is left alone.

- A start, a delete or an update of a service that is not stopped switches the app from desktop mode to the tray and performs instead of asking the user to quit HFDesk.
- Deleting the service in that switch returns the app to desktop mode.
- Updating a stopped service keeps the window open.

A service action no longer stops at "quit HFDesk and try again". The host closes into the tray through the same handover the installation uses, the action runs, and removing the registration returns the app to desktop mode. Updating a service that is confirmed stopped stays a pure rewrite in place, so a running desktop server keeps serving and its window stays open.

- The missing console program is found under either spelling of its version.
- A download of it that cannot be offered states the reason and offers **Try again** instead of a button that disappears.

The console program is matched whatever spelling its version takes, so a release asset named with a "v" pairs a build named without one, and the checksum lookup uses the same matching; verification itself stays fail-closed. When no verified download can be offered, the notice names the reason and offers **Try again** rather than dropping the button without a word.

- The log no longer records a state reading while nothing changes; it records state changes and actions.

An idle window with the log open stays quiet, and the log keeps what matters: transitions and the actions that caused them.

- A failed service installation now says what actually went wrong — the start did not run, the program ended too early, the service did not come up in time, or the started service could not be verified — instead of a vague "could not confirm".
- A registration removed after a failed installation attempt no longer reads as if the service had never been registered.

A failed start states its class once, in the headline, and keeps only the observed facts below it, such as the state and the exit code, with one next step. An installation that never reached a registration says exactly that, and a registration removed afterwards keeps the fact that one had existed.

- Installation and service actions now work while the Logs window or the web UI is open, without waiting for the open log view to end.

The live log stream ends on the shutdown signal instead of holding the drain to its deadline, so a handover to the tray no longer waits for an open log view; requests already in flight still finish normally.

- A service action that fails during the switch to the tray now shows one error window with the cause instead of two in a row.

The desktop knows the cause once the elevated helper is ready, so it reports it and the helper only records it.

- A first installation no longer reports that the just-created registration changed before its first start when nothing else touched it: the check now compares only what the installation itself wrote.

The check compares what decides which program runs — the command line strictly and first, then the service type, the start type, the error control and the account by identity — instead of guessing at fields the installation never wrote. The separate read-against-read check that guards against someone else's changes keeps every field and is unchanged.

- The service starts from any folder now, a user profile included: the installation gives the service account access to its own program, and refuses with instructions to move the pair instead of registering a service that cannot start.

A Windows service runs as a restricted account with no way into a user profile, which is why an installation from a Desktop or Downloads folder could not start. The installation now grants its own account read and execute on its program and the route to it — nothing wider, nothing removed — and where the machine will not allow that grant it refuses before the registration exists and names the fix.
