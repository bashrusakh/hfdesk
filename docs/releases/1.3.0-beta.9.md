### Changed

- The Windows desktop host's missing console notice can download the paired console program and continue the service action (#219).

At the install precheck and before either update entry reaches the administrator prompt, the notice is a task dialog: the missing file as its bold first line, the folder under it, a **Download it and continue** command link that fetches exactly that program of this release behind a progress dialog with **Cancel** and verifies its SHA-256 before placing it, a note line naming the action it continues, a **Not now** answer, and the manual steps in a collapsed **Install it manually instead** expander. The download is fail-closed: the release's `checksums.txt` is the authoritative checksum source, so a local build without a version and a release without a checksum asset get no offer and no file; a checksum mismatch, a failed transfer or a cancelled transfer leaves no file of its own and never touches a file the action did not place. Once the program is in place, the same service action continues through its usual confirmation and administrator prompt, and a start runs the registered program and never sees the notice.

- The Windows desktop host shows the service registration state on both of its surfaces, with install-service actions sharing one guarded flow (#219).

The tray menu starts with a status line — `Service: installed (running)`, `Service: not installed`, or `Service: unknown` when the state could not be read, which never claims a machine without a service — re-read after the host's service actions and every 30 seconds, so it reports the registered state rather than a cached one. With a service installed, **Install service…** stays visible but greyed beside a new **Service…** item that opens the same registered-service dialog (open, start or update); without one, **Install service…** is the active item with no dead second item beside it. The Runtime / Logs window shows the same status as a header chip and adds an **Install service…** button that is enabled only while no service is installed and runs the exact tray installation flow; the host's single-action guard refuses a second installation while one is in flight, whichever surface started it. Over HTTP, `POST /api/runtime/install-service` hands that same guarded flow to the host and `GET /api/runtime` carries the read as `serviceState`, so the window and the tray cannot drift apart.

- Cancelling a download (or cleaning a paused job's leftover part files) in local-folder mode now removes the directories its removed partials leave completely empty, up to the output root (#218).

In flat output mode, explicit-cancel cleanup and `CleanupJobPartFiles` walk the removed partial's directory chain upward while each directory is completely empty, stopping at the first directory that still holds content, is a symlink or non-directory, leaves the output root, or is held by a live writer; the output root itself and the HF cache layout are never pruned. Each removal takes the directory's tree-removal admission after the destination scope is released, so a concurrent writer is never disrupted, and pause and internal abort keep preserving resumable partials without pruning.

(Note: this text intentionally says `Service: installed (running)` — that is what the published beta.9 artifacts actually ship; the presence-only wording landed after the release and stays in `[Unreleased]`.)
